B2. FACE RECOGNITION INTEGRATION
──────────────────────────────────────────────────────────────────────────────

PRIMARY FILE: services/face_service.py

  Function: process_face_image(image_b64, student_id) → dict
  ───────────────────────────────────────────────────────────
  Called when a student is registered (POST /api/register).
  The current implementation is COMPLETE — it will work once the
  face-recognition and opencv-python packages are installed.

  What it does:
    1. Base64-decode the image
    2. Detect face locations (face_recognition.face_locations)
    3. Extract 128-d encoding (face_recognition.face_encodings)
    4. Save the image to static/faces/<student_id>.jpg
    5. Return {"image": filename, "face_encoding": pickle.dumps(encoding)}
  The encoding BLOB is stored in the students table (face_encoding column).

  Function: compare_face(unknown_image_b64) → dict
  ──────────────────────────────────────────────────
  Called by services/attendance_engine.py → verify_face() (Step 2).
  STATUS: NotImplementedError — implement this function.

  Steps (see detailed docstring in the file):
    1. Call cache.face_cache.get_known_faces() → {student_id: np.array(128,)}
    2. Decode the unknown image and extract its encoding
    3. Compute: distances = np.linalg.norm(matrix - unknown_enc, axis=1)
    4. Find best match: best_idx = np.argmin(distances)
    5. Compare distance against config thresholds:
         < FACE_FLAGGED_DISTANCE_MIN (0.50) → safe match
         0.50 – FACE_FLAGGED_DISTANCE_MAX (0.65) → flagged (accepted, marked)
         > 0.65 → rejected (return matched=False)
    6. Return {"matched": True, "student_id": ..., "distance": ..., "is_flagged": ...}

  After implementing compare_face():
    - The "face_simulated" flag in attendance records will stop appearing.
    - Students without face encodings will be rejected at Step 2.

  SECONDARY FILE: cache/face_cache.py
    The _load_from_db() function is already implemented.
    Just install numpy + face-recognition and it will work.

B3. GPS / GEOFENCE INTEGRATION
──────────────────────────────────────────────────────────────────────────────

PRIMARY FILE: services/geofence_service.py
  STATUS: FULLY IMPLEMENTED — no code changes needed.

  To activate geofencing:
    1. Add GPS coordinates to each room record:
         POST /api/rooms with body:
         {
           "name": "Room 401",
           "latitude": 41.015137,
           "longitude": 28.979530,
           "geofence_radius": 40
         }
    2. Link the room to the course schedule:
         In the course's schedule dict: {"room_id": <room_id>, ...}

  When a room has no GPS coordinates, the geofence check is bypassed and
  the attendance is flagged with "warning: Room GPS not configured".

  Fake GPS detection is active for:
    - accuracy == 0.0  (mock GPS apps often report exact 0)
    - speed > 30 m/s   (108 km/h — student was in a vehicle)
    - GPS timestamp older than 30s when received by server (replayed location)

  Mobile side (mobile-app/app/shared/services/locationService.js):
    Send accuracy and speed fields alongside lat/lng:
    {
      "session_id": "...",
      "latitude": 41.015,
      "longitude": 28.979,
      "accuracy": 12.5,    ← from expo-location result.coords.accuracy
      "speed": 0.3         ← from expo-location result.coords.speed
    }

B4. QR SCAN INTEGRATION
──────────────────────────────────────────────────────────────────────────────

PRIMARY FILE: services/qr_service.py
  STATUS: FULLY IMPLEMENTED — no code changes needed on the backend.

  QR content format:
    "smartattendance://course/<COURSE_CODE>"
    Example: "smartattendance://course/AI101"

  The QR is STATIC PER COURSE. The instructor puts it on their slides once.
  Security is enforced by GPS (Step 1) and Face (Step 2) preceding this step.

  Backend checks performed in verify_qr_against_session():
    1. Session status == 'active'
    2. QR course code matches the session's course code
    3. (Enrollment check is done in attendance_engine.py)

  Mobile side:
    Use expo-barcode-scanner or expo-camera with barcode scanning:
    import { BarCodeScanner } from 'expo-barcode-scanner';
    Send the scanned value to POST /api/verify/qr:
    {
      "step_id":    "...",   ← from Step 1 response
      "session_id": "...",   ← from active session
      "qr_code":    "smartattendance://course/AI101"
    }

  For the instructor dashboard (optional):
    Generate QR images server-side:
    pip install qrcode[pil]
    Then call: services/qr_service.generate_qr_image(course_code, output_path)

B5. ATTENDANCE ENGINE — 3-STEP FLOW OVERVIEW
──────────────────────────────────────────────────────────────────────────────

FILE: services/attendance_engine.py

  The engine is the orchestrator. Integration points are clearly marked
  with "── INTEGRATION POINT ──" comments in each method.

  Flow:

    Student opens app
          │
    POST /api/verify/location  ← Step 1
    Body: { session_id, latitude, longitude, accuracy, speed }
    Response: { success, inside, distance_m, step_id }   ← SAVE step_id
          │
    POST /api/verify/face      ← Step 2
    Body: { step_id, image }
    Response: { success, face_verified, face_score }
          │
    POST /api/verify/qr        ← Step 3
    Body: { step_id, session_id, qr_code }
    Response: { success, attendance_record, is_flagged, flag_reason }

  Timing window: 120 seconds between Step 1 and Step 3.
  If exceeded, the step record is deleted and the student must restart.

  The step_id is a UUID stored in the attendance_steps table.
  After Step 3 succeeds, the step record is automatically deleted.

B6. DATABASE — SWITCH TO SQLITE
──────────────────────────────────────────────────────────────────────────────

Current default: JSON files in static/
To switch to SQLite, add to your .env file:

  DB_DRIVER=sqlite
  SQLITE_PATH=smart_attendance.db

The SQLite schema is created automatically on first run.
No migration scripts needed. WAL mode is activated automatically.

To migrate existing JSON data:
  Write a one-time migration script that reads from JSONAdapter
  and writes to SQLiteAdapter. No tool is provided for this yet.

B7. ADDING THE /api/auth/me ENDPOINT (Recommended)
──────────────────────────────────────────────────────────────────────────────

FILE: routes/auth.py

  Add this endpoint so mobile app restoreSession() can verify the token
  and get fresh user data without storing it locally:

    @auth_bp.route('/auth/me', methods=['GET'])
    @jwt_required()
    def get_me():
        identity = get_jwt_identity()
        db = get_db()
        user = db.get_user(identity['username'])
        if not user:
            return jsonify({'success': False, 'message': 'User not found'}), 404
        return jsonify({
            'success': True,
            'user': {k: v for k, v in user.items() if k != 'password'}
        })

  Then update mobile-app/app/shared/store/authStore.js restoreSession()
  to call /api/auth/me instead of /api/users.
